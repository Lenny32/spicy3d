# Merging two versions of a document

How two divergent versions of a Spicy3D document are merged against their common base (CLOUD-11).
This is the specification the merge engine (CLOUD-12, `packages/core/src/merge/`) implements and the
conflict panel (CLOUD-13) presents. What it rests on in the code:

| What | Where |
|------|-------|
| Conflict, change, resolution and result types; the path helpers | `packages/core/src/merge/types.ts` |
| The rule vocabulary and registry (`MergeRules`) | `packages/core/src/merge/rules.ts` |
| Rules of every serializable class and stored payload | `core/src/merge/coreRules.ts`, `parametric/src/mergeRules.ts`, `app/src/bodys/mergeRules.ts`, `wasm/src/mergeRules.ts` — generated list [below](#rules-of-every-class) |
| Fixture corpus (the expected answers) | `packages/core/test/fixtures/merge/<case>/`, generated by `packages/core/test/merge/fixtureCases.ts` |
| Globally unique sketch ids | `packages/parametric/src/sketch/sketchIds.ts` ([Unique ids](#unique-ids)) |
| The engine: `mergeDocuments`, `resolveMerge` / `applyResolutions`, `diffDocuments` | `core/src/merge/merge.ts` (run, integrity, positions), `structural.ts` (the three-way rule over the rules), `listOrder.ts` (patience diff3 of id lists), `integrity.ts`, `diff.ts` |
| Validation pass: `validateMerge`, `collectRebuildReport`, `IMergeEvaluator` | `core/src/merge/validation.ts`; the app's `HeadlessDocumentEvaluator` (`app/src/mergeEvaluator.ts`, registered by `Application`) |
| Applying a merge to the open document: `applyMergeToDocument`, `IDocument.replaceContent` | `core/src/merge/apply.ts`, `core/src/documentContent.ts`, `ModelManager.applyContent` |
| Compare lines (version history): `SemanticDiffer`, `summarizeChanges`, `compareDocuments` | `core/src/documentDiff.ts` |

## Scope

- **Who conflicts.** Documents are never shared (tickets/cloud/README.md), so the two sides are always
  the same user: two devices, two tabs, or the user and an MCP agent. Mostly after offline work.
- **When.** At save time, over the version DAG: the sync (CLOUD-10) sees the head moved since its base
  version and merges `base` (the version both started from), `ours` (this device's unsaved state) and
  `theirs` (the server head). The result is saved as a two-parent `merge` version.
- **Where.** Client-side only. The validation pass needs the WASM kernel; the server stores documents
  as opaque manifests.
- **How.** A semantic three-way merge keyed by stable ids over the *serialized* document, then a
  referential-integrity pass and a rebuild check. Line-based JSON merging is useless here (payloads
  are JSON strings inside JSON; order and ids carry meaning). Last-writer-wins is used for the
  document name only.
- **Purity.** `mergeDocuments(base, ours, theirs, rules)` is a pure, deterministic function of its
  inputs (same inputs → byte-identical `merged`, same conflicts in the same order). Inputs are never
  mutated. Only the validation pass touches the kernel, after the structural merge.
- **Identities** (property-tested in CLOUD-12): `merge(b, x, b) = x`, `merge(b, b, y) = y`,
  `merge(b, x, x) = x`, all without conflicts.

## Inputs

All three inputs are migrated to this build's format first (`DocumentMigrations.migrate`, which never
touches `userData`); a document the build cannot migrate (newer format, not Spicy3D) is not merged —
`mergeDocuments` returns the error (`{ kind: "format", side }`, or `differentDocuments` when the ids
differ) and the user keeps "save mine as a copy". Cloud versions are manifests (`documentManifest.ts`):
large values are `{ "$blob": sha256 }` references.

**How the merge sees documents.** Documents are merged in the form they are given — assembled
(`Serialized` with every value inline), manifests, or a mix — and a value is compared with a
reference **by hash**: an inline value is hashed the way `splitManifest` would store it (UTF-8 for a
string, the `$as` encoding for number arrays; a synchronous SHA-256, `sha256.ts`), so `ours` assembled
against a manifest `base` / `theirs` gives no spurious conflict whatever the thresholds were. Blobs are
never downloaded to compare. A JSON payload stored as a reference is parsed when another input has
the same text inline (same hash); otherwise it cannot be merged inside and is one value. `merged` keeps
a value inline whenever any input had it inline; a reference remains only where no input held the
content (the caller assembles it from its blob cache). CLOUD-10 passes the local side assembled and
the others as they come from the cache — assembling payload blobs first gives the finest merge.

The serialized envelope (`app/src/document.ts` `serialize()`, fixture
`packages/core/test/fixtures/documents/v1/rich.json`):

```jsonc
{
  "__cla$$__": "Document", "formatVersion": 1, "moduleVersions": { "parametric": 1, "sketch": 1 },
  "id": "…", "name": "…",
  "models": {
    "nodes": [ /* flat, pre-order: { "__cla$$__", "id", "parentId"?, …@serialize() props } */ ],
    "materials": [ /* { "__cla$$__": "Material" | "PhongMaterial" | …, "id", … } */ ],
    "components": [ /* { "__cla$$__": "Component", "id", "name", "origin", "nodes": [inline] } */ ]
  },
  "variables": [ { "id", "name", "type", "expression", "description"? } ],
  "settings": { "lengthUnit"? },
  "acts": [ { "__cla$$__": "Act", "name", "cameraPosition", "cameraTarget", "cameraUp" } ],
  "userData": { /* opaque to Spicy3D */ }
}
```

- **The tree** (`NodeUtils.serializeNode`, `core/src/model/node.ts`): `models.nodes` is the tree
  flattened depth-first, pre-order. The first node is the root folder (no `parentId`); every other
  node has `parentId`, which precedes it in the array; sibling order is array order. The merge
  output is re-flattened the same way.
- **Payloads stored as JSON strings.** The serializer only round-trips `@serializable` classes, so
  plain object graphs are stored as strings and must be parsed to be merged:
  `ParametricBodyNode.featuresJson` (`FeatureData[]`, `parametric/src/features/feature.ts`),
  `SketchNode.dataJson` (`SketchData`, `parametric/src/sketch/sketchModel.ts`),
  `SketchNode.planeRefJson` (`PlaneFaceRef`), `SketchNode.constructionPlaneRefJson` and the refs inside
  `ConstructionNode.definitionJson` (`ConstructionRef`, `core/src/construction/types.ts`),
  `AnalysisNode.sourcesJson` / `settingsJson`. The merged value is written back with
  `JSON.stringify` of the merged object (key order: the order of the side the object came from,
  new keys appended — irrelevant to equality, but deterministic).
- **Values with a class** (`{ "__cla$$__": "XYZ", … }`, `Plane`, `Matrix4`, kernel shapes `OccSolid`…)
  follow their class's rule (a value or a blob).

## Pipeline

1. Migrate the three inputs; refuse unmigratable ones. Check `base.id = ours.id = theirs.id`.
   (`mergeDocuments(base, ours, theirs, rules?)` → `Result<MergeResult, MergeError>`; `MergeResult`
   carries the migrated `inputs`, from which `resolveMerge(result, choices)` re-merges.)
2. Parse every JSON payload (a payload that does not parse is merged as one atomic string).
3. Structural three-way merge, top-down: [document fields](#document-fields), document lists
   (variables, acts, materials, components), [the node set](#node-set), [each node's properties and
   payloads](#properties-and-payloads) (features, sketches), then [the tree](#tree) (moves, cycles,
   sibling order).
4. [Timeline positions](#timeline-positions) are merged as feature ids and projected onto the merged
   feature lists.
5. [Post-merge normalization](#post-merge-normalization) of derived state.
6. [Referential integrity](#referential-integrity): every reference must resolve; merge-introduced
   dangling references become conflicts; variable names stay unique.
7. Serialize (pre-order tree, payloads re-stringified). This is `merged`; it is always loadable.
8. [Validation](#validation-pass-wasm) (kernel, `validateMerge`, asynchronous): rebuild; failures
   introduced by the merge become `rebuild-failure` conflicts.
9. `changes` = the [changes](#change-model-diff-and-compare) from `ours` to `merged`.

## The three-way rule

For one value `b`, `o`, `t` (absent = the key is missing, `undefined` or `null` — the deserializer
treats `null` as absent):

| Situation | Result |
|-----------|--------|
| `o = t` | `o` (covers "unchanged", and "both made the same change") |
| `o = b` | `t` |
| `t = b` | `o` |
| otherwise | conflict (kind by rule: `property`, `blob`, `move`, …); `merged` holds `o` |

**Equality is exact, structural JSON equality**: same type; numbers by `Object.is` (no tolerance: a
parameter that changed by 1e-12 changed); strings exactly; arrays element by element; objects by key
set and values, key order ignored; a `$blob` reference by its hash. Rules decide the granularity —
what is one value:

- **Defaults** for a property no rule lists: a JSON primitive is `scalar`; an object with
  `__cla$$__` follows its class (`value` → one value; `blob` → one value, `blob` conflicts); a
  `{ "$blob": … }` reference is a `blob`; any other array or object is `atomic` (one value).
  Matrices, vectors, planes, colors, point lists and blobs are therefore atomic.
- A rule can go finer (`object` field by field, id-keyed `list`, `map` per key, a `json` payload) or
  declare a value `derived` (recomputed by the rebuild — never a conflict: the side that changed it,
  else ours), `lww`, `max` / `min`.
- `max` / `min` apply the three-way rule first — an absent value is a side's change like any other
  (a side that dropped the counter changed it) — and only when both sides changed it to different
  numbers does the larger / smaller win; if one of them dropped it, the removal wins.
- An `object` rule may name **groups**: fields that are alternatives of one choice (a revolve's axis
  snapshot / picked edge / construction axis; an extrude's sketch + profiles / press-pull source).
  A group is one value at `…/<group name>` — merging its fields separately could combine one side's
  axis edge with the other's construction axis.

## Document fields

| Field | Rule |
|-------|------|
| `id` | Must be equal on all sides (else: not the same document, refuse). |
| `name` | Last writer wins: both changed → `theirs` (the head, saved last), no conflict. |
| `formatVersion`, `moduleVersions` | This build's (all inputs are migrated). |
| `settings` | Per key, three-way `scalar` (`doc/settings/<key>`). |
| `userData` | Per top-level key, three-way `atomic` (`doc/userData/<key>`); never interpreted. |
| `variables` | Id-keyed list, stable order (below): per field — `name`, `type`, `description` scalar, `expression` an expression. |
| `acts` | Keyed by `name` (acts have no id; the n-th act of one name is its n-th occurrence, path `act/<name>/#<n>` for n ≥ 2 — a separate segment, so an act named `View#2` stays `act/View#2`), stable order; each camera field atomic. |
| `models.materials` | Id-keyed records: every field on its own; a texture (with its data-URL image) atomic. |
| `models.components` | Id-keyed records: `name` scalar, `origin` atomic, `nodes` (stored inline) atomic. |

Variables resolve top-down: a variable may only use the ones above it (`evaluateVariables`). Their
order is merged like any stable list; the [integrity pass](#referential-integrity) then checks
every expression against the merged table.

## Node set

Nodes are matched by `id` (a nanoid). Per id:

| base | ours | theirs | Result |
|------|------|--------|--------|
| – | added | – | added (same for theirs) |
| – | added | added, equal | added once |
| – | added | added, different | `duplicate-id` at `node/<id>` (merged: ours) — nanoids make this practically impossible, it guards hand edits and bugs |
| present | deleted | unchanged | deleted |
| present | deleted | deleted | deleted |
| present | deleted | **modified** | `delete-vs-modify` at `node/<id>` (merged: deleted — ours) |
| present | **modified** | deleted | `delete-vs-modify` at `node/<id>` (merged: kept, ours' version) |

`merged` holds the first choice, `ours`: this device's state — the deletion when this device deleted
it, the edited node when this device edited what the other deleted — so an unresolved merge is always
"mine plus every non-conflicting change of theirs". (Fixtures `delete-node-vs-modify` and
`delete-node-vs-modify-theirs-deleted`.)

A node is **modified** when any of its properties or payloads changed, when it **moved to another
parent** (a delete never silently beats a move — fixture `delete-node-vs-move`; a new position among
the same siblings is not a modification), or when the other side **added a node under it** or **moved
a node into it** (its subtree grew). Deleting a node deletes its subtree; a modified descendant makes its own `delete-vs-modify`
(on the descendant). A node **kept** against the other side's deletion (ours by default, theirs when
chosen) is kept with its subtree as the keeping side has it — except descendants a resolution deletes —
and with every ancestor the other side deleted with it, all with the keeping side's content. References *to* a deleted node from the other side's changes (a
feature's `sketchId`, a boolean tool, a sketch's plane face) are found by the
[integrity pass](#referential-integrity) as `dangling-ref` on the referrer — e.g. deleting a sketch
the other side started extruding.

A node whose class this build does not register (`UnknownNode`, a plugin not loaded) is merged by
`UNKNOWN_CLASS_RULE`: its tree position like any node, everything else as one value.

## Properties and payloads

Every property of a node present on all sides is merged by its class's rule (the [generated
list](#rules-of-every-class)): `name`, `visible` scalar; `transform`, `materialId`,
`faceMaterialPair` atomic; primitive parameters (`dx`, `radius`, …) scalar; points, vectors and
planes atomic; captured input shapes of the old operation bodies (`BooleanNode.booleanShape`,
`ExtrudeNode.section`, …) and imported geometry (`EditableShapeNode.shape`, `MultiShapeNode.shapes`,
`MeshNode.mesh`) are blobs: both replaced differently → `blob` conflict at `node/<id>/prop/<property>`.
`parentId` is the [tree](#tree)'s.

A `json` property is parsed and merged by its payload rule; the conflicts inside use the payload's
own path segments (`feature/…`, `entity/…`), never the property name, so a future storage change
keeps the paths.

### Ordered, id-keyed lists

Used for the timeline, sketch arrays, variables, acts, materials, components and siblings in the
tree. Items are matched by their key; the item's content is merged by the item rule; the **order**
is merged by diff3 over the key sequences:

1. **Deletions.** An item deleted by one side and unchanged by the other is deleted; deleted vs
   modified is `delete-vs-modify` at the item's path (merged: ours — deleted, or ours' edit).
2. **Placements.** For each side, the *stable* items are those of the longest common subsequence of
   base and that side (among several, the one keeping the earliest base items — e.g. base `f1 f2 f3`,
   side `f1 f3 f2`: `f1 f2` stay, `f3` moved). Every other item of the side is *placed* (inserted,
   or moved): its **anchor** is the nearest stable item before it in that side (or the start).
   With unique keys the LCS is the longest increasing run of the side's base indexes — patience
   sorting, O(n log n): a 10 000-sibling list merges in about 0.15 s (`mergePerformance.test.ts`).
3. **Merge.** The skeleton is base's items **stable on both sides** (an item one side moved is that
   side's placement), minus deletions, in base order; each placement is put right after its anchor,
   wherever the anchor ends up. The same item placed by both sides after the same anchor is one
   placement (emitted once). If the anchor was deleted, the placement falls back to the nearest
   surviving item before it in the placing side's sequence (or the start). Several placements at one
   anchor: ours first (in ours' order), then theirs. Placements anchored at each other in a loop (each
   side kept the other's item stable) come last, ours' order then theirs'.
4. **Order semantics** depend on the list:
   - `timeline` (the feature list — order is geometry):
     - the same item placed by both sides at different anchors → `order` conflict at
       `…/feature/<id>/position` (values: the anchors, `null` for the start; merged: ours);
     - both sides placing *different* items at the same anchor → one `order` conflict at
       `node/<body>/insertAfter/<anchor>` or `node/<body>/insertAtStart` (values: the ids each side
       placed; choices `ours-first` (merged), `theirs-first`, `ours`, `theirs` — the last two drop
       the other side's placements there);
   - `stable` (siblings, sketch arrays, variables, acts, materials, components — order is
     incidental): never a conflict; the same item moved differently keeps ours' placement.

## Features

`ParametricBodyNode.featuresJson` is the body's whole content (shapes are replayed through
`registerFeature` handlers). It merges as a `timeline` list of `feature` by `id` (a nanoid), each
feature by its `type`:

- A feature's `type` never changes; if it differs, the whole feature is one value.
- **Parameters** merge one by one (`node/<body>/feature/<id>/param/<key>`): `depth`, `startOffset`,
  `angle`, `radius`, `distance` are expressions (a number or an expression string — the value, not
  what it evaluates to); `symmetric`, `operation`, `consumeTools`, `suppressed`, `name` scalar.
  Parameters of different features, or different parameters of one feature, never conflict.
- **Selections are one value each**: `edges` (`EdgeRef[]`), `profiles` (`ProfileRef[]`), `source`
  (press-pull face), `axis`, `axisSource`, `constructionAxisRef`, `toolIds` (their order is the order
  of the tool id ranges, `operationIds.ts`). The user picked them as a whole; merging a union of two
  edge picks would fillet edges nobody chose together.
- **Alternatives are one group**: an extrude's input `sketchId` + `profiles` + `source` (a sketch or
  press-pull faces) at `…/param/input`; a revolve's `sketchId` + `profiles` at `…/param/input` and its
  axis `axis` + `axisSource` + `constructionAxisRef` at `…/param/axis`.
- **Extents** (parametric 3): an extrude's `extent` / `secondExtent` merge by their `type`; a changed
  type is one value. A to-object extent's `face` (a `ProfileRef`) + `nodeId` are one pick, its `offset`
  an expression of its own.
- **References** (checked by the integrity pass): `sketchId`, `source.nodeId`, `axisSource.nodeId`,
  `extent.nodeId`, `toolIds` → nodes; `edges[].edgeId`, `axisSource.edge.edgeId`, `source.profiles[].id`,
  `extent.face.id` → tracked sub-shape ids; `profiles[].entities` → entities of the feature's sketch; `constructionAxisRef` → a
  construction ref (its `featureIndex` a timeline position).
- A feature type this build does not know: base fields as above, every other field one value.
- Consumed boolean tools are the body's children in the tree; the child relation is re-derived from
  the merged features when the body loads (`syncConsumedTools`), so a tree/feature disagreement
  resolves in favour of the features.

## Sketches

`SketchNode.dataJson` (`SketchData`) merges field by field:

- `entities`: `stable` list of `entity` by `id`. `params` (the geometry) is **one value per
  entity**; `type` scalar (never changes); `construction` scalar; a bspline's `parametrization`
  and `periodic` scalar each (its fit points are its `params`, so a fit point added on one device and
  another moved on the other is one `params` conflict). Two devices moving one line
  differently → `property` conflict at `node/<sketch>/entity/<id>/params`.
- `constraints`: `stable` list of `constraint` by `id`; `kind` scalar; `refs` one value that must
  resolve (every `entityId` a merged entity, a datum id −1…−3, or a merged external); `datum` an
  expression, `datums`, `blockedParams`, `direction` one value each. Structural constraints (an arc's
  `PointOnArc`, an ellipse's `Perpendicular`) travel with the entity that added them.
- `anchors` (dimension label positions): keyed by the constraint id they belong to; an anchor
  whose constraint is gone is dropped silently (the solver does the same, `anchors.filter(retained)`).
- `externalRefs`: `stable` list of `external` by `entityId`; `nodeId` → node, `edge` → `EdgeRef`;
  `role`, `pinned` scalar; the resolution results `type`, `snapshot`, `dangling` are derived.
- `refPositions`: per body id, a [timeline position](#timeline-positions).
- `entityIdSeq` / `externalIdSeq`: legacy counters (see [Unique ids](#unique-ids)) — max / min.

`SketchNode.plane` is one value (a snapshot the plane reference re-derives), `planeRefJson` one value
(`PlaneFaceRef`: its `nodeId` and tracked `faceId` must resolve), `constructionPlaneRefJson` one
`ConstructionRef`. A sketch's entities and constraints are merged by id **because the ids are globally
unique** — see [Unique ids](#unique-ids): two lines drawn on two devices never share an id, so
both are kept (fixture `both-add-sketch-line`).

## Construction geometry

`ConstructionNode.definitionJson` (`ConstructionDefinition`, paths `node/<id>/definition/<field>`): a
changed `kind` makes the whole definition one value (the other fields change meaning); otherwise field
by field, each `ConstructionRef` one value (`CONSTRUCTION_REF_RULE`, `rules.ts`) whose `nodeId`, tracked
ids (`trackedId`, `incidentEdgeIds`) must resolve and whose `featureIndex` is a
[timeline position](#timeline-positions) in the body its `nodeId` names — nested refs (a snap's
`source`, a path's `segments`) likewise. The lengths and angles (`distance`, `offset`, `angle`; document
format 2) are parameters like a feature's: a number or an expression whose names must be variables; a
path `position` is one value (its distance `value` an expression). The same rule covers `SketchNode.constructionPlaneRefJson`
(payload `construction.ref`, path `node/<id>/constructionPlaneRef`) and a revolve's
`constructionAxisRef`. Fixture `construction-anchor-remap`: a datum captured after `f2` (featureIndex
2), the other side inserted a feature before `f2` → 3.

## Tree

- `parentId` is merged three-way: both moved one node to different parents → `move` conflict at
  `node/<id>/parent` (merged: ours). A parent that is gone falls back to ours' parent, else theirs',
  else base's. With none left, a node only one side has (added under a node the other side deleted —
  that deletion's `delete-vs-modify` reports it) goes with its parent; a node **both sides kept is
  never dropped**: the parent chain of the side chosen at `node/<id>/parent` (ours by default) comes
  back with it (the other side had deleted it), reported as a `move` there (fixture
  `tree-kept-node-parents-gone`).
- A node moved into a node the other side deleted: that is a modification of the deleted node →
  `delete-vs-modify` at the deleted node; merged: the deletion, the moved node at ours' parent.
- **Cycles.** Moves fine on their own can close a cycle together (ours: A into B; theirs: B into A).
  After applying parent changes, while a cycle exists: **one** node is reverted — the first in base
  pre-order of the cycle's nodes whose merged parent came from theirs, else from ours, else any, a
  parent a resolution chose last — to the first of ours', theirs', base's parents that is present and
  outside the cycle (else the root), and one `cycle` conflict is reported for it at `node/<id>/parent`
  (values: its parent on each side; args: its name and the name of the node it was to go into); then
  the tree is checked again. Every revert leaves its cycle, so this terminates; one conflict per
  reverted node, never a revert without one (fixtures `tree-move-two-cycles`,
  `tree-cycle-into-deleted-parent`). `theirs` on a node theirs moved keeps that move and reverts ours'
  moves in that cycle. A child no side has under its merged parent (a cycle broken to the root) is
  placed after its siblings, in base, then ours', then theirs' pre-order.
- Sibling order: each parent's children are a `stable` list (fixture `both-add-nodes`: both
  appended, ours first).
- The root node (the first) is never moved or deleted.

## Timeline positions

Some values are *positions in a body's timeline* — a feature count: `SketchData.refPositions[bodyId]`
(the sketch was captured against the body's first n features; `computeSketchRollback` rolls the
body back there) and `ConstructionRef.featureIndex` (body = its `nodeId`). A position means "after
that feature", so merging the numbers is wrong once the other side inserted earlier features.
Positions merge as **anchor ids**:

1. On each side, `anchor(side) = n ≤ 0 ? START : side's feature list[min(n, length) − 1].id`.
2. Three-way on the anchors (not the numbers): one side re-anchored → that side; both, differently →
   `property` conflict at the position's path.
3. Project onto the merged feature list: `START` → 0; an id → its merged index + 1. An anchor feature
   missing from the merged list falls back to the nearest earlier feature of the side the anchor came
   from that survives (or 0). A position into a deleted body is dropped (the references to that body
   report it).

Because anchors are compared, `merge(b, b, y) = y` holds even when `y` inserted features and kept the
old number (the app does not renumber anchors on insert). When the merged feature list of the body is
exactly the list of the side the value came from, that side's number is kept as it is (a number past
the end stays past the end). Positions inside atomic values — every `ConstructionRef.featureIndex`,
declared `timeline-position` with `bodyFrom: "nodeId"` — are compared and projected the same way. Fixture `timeline-anchor-remap`: this device
put a sketch on the body's top face anchored at 2 (after `f2`); the other inserted a feature before
`f2` → the merged anchor is 3.

## Post-merge normalization

Derived state recomputed from the merged content before the integrity pass, never a conflict — only
for a payload the merge actually combined (one that equals a side's stays byte for byte; the payload
rule's `normalize`, `sketch.data`'s in `parametric/src/mergeRules.ts`):

- `syncExternalRoles` on every sketch: an unpinned external ref's `role` follows the constraints now
  referencing it (a pinned role is the user's and stays as merged).
- Dimension anchors of removed constraints are dropped.
- `formatVersion` / `moduleVersions` are this build's.

## Referential integrity

Every reference in the merged document must resolve:

| Reference | Resolves when |
|-----------|---------------|
| node (`sketchId`, `toolIds`, `source.nodeId`, `axisSource.nodeId`, `externalRefs[].nodeId`, analysis sources, `planeRefJson.nodeId`) | the node exists in the merged tree |
| material (`materialId`), component (`componentId`) | the id exists in `models.materials` / `models.components` |
| sketch entity (`constraints[].refs[].entityId`) | an entity or external of the same merged sketch, or a datum id (−1, −2, −3) |
| sketch constraint (`anchors[].id`) | a constraint of the same sketch (else dropped, above) |
| tracked sub-shape id (`EdgeRef.edgeId`, `ProfileRef.id`, `PlaneFaceRef.faceId`, `ConstructionRef.trackedId`/`incidentEdgeIds`) | every `\|`-component names an existing source: `<featureId>:…` a feature of that body *before* the referring feature in the merged timeline (or any feature of it, for a reference from outside the body); `sketch:<sketchId>:…` (sweep seeds of an extrude / revolve / loft) such a feature that swept that sketch (a loft sweeps each of its sections' sketches); `tool:<nodeId>:…` an existing node |
| sketch entity of a profile (`ProfileRef.entities`) | an entity of the feature's sketch |
| variable name | unique in the merged table (below) |
| variable (names in an expression: feature parameters, construction lengths and angles, constraint `datum`/`datums`, variable expressions) | a variable of that name exists — for a variable's own expression, *above* it |
| timeline position | the body exists |

Tracked ids are derived from feature ids and kernel history (`trackedId.ts`, `operationIds.ts`:
`<featureId>:<n>`, compounds `a|b`, `tool:<nodeId>:<n>`, sweep seeds `sketch:<sketchId>:<seed>…` from
the swept sketch's entities, `extrude.ts` / `revolve.ts` / `loft.ts`), so their source is readable without the
kernel. Whether a surviving source still produces *that* edge is the
validation pass's question.

A reference that does not resolve is reported as `dangling-ref` at the referrer's path (args: the
referrer's label and the missing target) **only if the merge introduced it**: a parent has the same
value at that path, and in every parent that has it, it resolved. Dangling references already present
in a parent are left alone. Choices: `accept` (merged: kept as it is; the feature shows its error
until fixed), `ours` / `theirs` (take that side's version of both the referrer — the innermost item
holding the reference: the feature, entity, constraint, external, variable or node — and the missing
target, whole; the pass runs again, new dangling references become new conflicts).

**Variable names stay unique.** Two variables of one name after the merge (both sides added
`thickness`, or one renamed onto a name the other added) would let `evaluateVariables` keep the first
and silently change the other side's geometry. Unless a parent already had that duplication, it is a
`duplicate-id` conflict at `variable/<id>/name` of the later one (message
`merge.conflict.duplicateName{0}`, args: the name; choices `ours` / `theirs`: every variable of that
name taken as that side has it). Merged holds ours: the other side's definition is dropped (fixture
`variables-same-name-both-add`).

Examples: this device deleted the boss extrude `f3`, the other filleted its top edge (`edgeId: "f3:2"`)
→ `dangling-ref` at `node/body-1/feature/boss-fillet/param/edges`; this device renamed variable `w`
to `width`, the other set a depth to `w / 4` → `dangling-ref` at `…/feature/f1/param/depth`
(renaming does not rewrite expressions in the app either, so the merge does not guess).

## Validation pass (WASM)

`validateMerge(result, { evaluator?, ours?, theirs?, onProgress?, signal? })` →
`Result<MergeResult, RebuildError>`; the evaluator (`IMergeEvaluator`, default `MergeEvaluators.current`
— the app's `HeadlessDocumentEvaluator`) loads a version into a headless document
(`Document.loadHeadless`: a `NullVisual`, not among the open documents, disposed after) and
`collectRebuildReport` rebuilds it node by node (a node reports itself through `IRebuildStatusSource`:
a parametric body per feature, a construction its resolution; other shape nodes their `shape`).

1. Load `merged` into a document without views (null visual), migrations already applied.
2. Evaluate every body and sketch; record per-feature status (`ParametricBodyNode` feature errors)
   and per-node shape status (sketch solve, construction resolution, `generateShape`).
3. Do the same for `ours` and `theirs` (cached from the sides' own last rebuild where available).
4. A feature (or node) failing in `merged` but succeeding in every parent that has it →
   `rebuild-failure` at `node/<body>/feature/<id>/rebuild` (or `node/<id>/rebuild`), args: label and
   the error message. Failures present in a parent are ignored; a location already reported as
   `dangling-ref` is not reported again. Only choice: `accept` — the UI offers "open the failing
   feature", edit, re-validate.

It is slow on big models: `onProgress(done, total)` after every node (over the documents rebuilt) and
cancel through the `AbortSignal` (`cancelled`; the event loop gets its turn between nodes); the
structural result is usable before it finishes. Fixture `rebuild-failure-thin-wall`: a thinner wall
here, a bigger fillet there — structurally clean, the fillet fails only in the merge.

## Applying a merge

`applyMergeToDocument(document, result, choices)` applies the resolved merge to the open document as
**one undoable step** (`merge`), before the merged version is pushed (CLOUD-13's "Undo merge"): it calls
`IDocument.replaceContent(merged, name)` — the same in-place reload CLOUD-10 needs for a pull. The
document object, its views and cameras stay; `ModelManager.applyContent` keeps every node whose
serialized form and parent are unchanged (the same object, moved into its new position), removes or
creates the others, and notifies observers once with the tree in its final state (a body referencing a
replaced sketch re-evaluates against the new one). The undo record (`DocumentContentRecord`) applies
the snapshot from before / after.

## Conflicts

`MergeConflict = { kind, path, base, ours, theirs, messageKey, args, choices }` (`types.ts`). `base` /
`ours` / `theirs` are the serialized values at `path` on each side (a missing key = absent there).
`merged` always holds the first choice. `CONFLICT_MESSAGE_KEYS` maps each kind to its message;
`args[0]` is the label of the item concerned (a node's `name`; a feature's `name`, else
`<type> <id>`; a sketch entity `<type> <id>`; a constraint `constraint <id>`; a variable its name).

| Kind | When | Path | Choices (first = merged) | Args |
|------|------|------|---------------------------|------|
| `property` | both changed one value differently | the value | `ours`, `theirs` | label, field |
| `delete-vs-modify` | deleted on one side, modified (or grown) on the other | the item | `ours`, `theirs` | label |
| `move` | one node moved to two parents | `node/<id>/parent` | `ours`, `theirs` | label |
| `cycle` | the sides' moves together make a cycle | `node/<id>/parent` of the reverted node | `ours`, `theirs` | label, label of the other node |
| `order` | timeline: one feature placed differently, or both placed at one anchor (`merge.conflict.insertAt{0}`) | `…/feature/<id>/position`, `node/<body>/insertAfter/<id>`, `node/<body>/insertAtStart` | `ours`, `theirs` / `ours-first`, `theirs-first`, `ours`, `theirs` | label (feature / body) |
| `dangling-ref` | a merge-introduced reference to nothing | the referrer | `accept`, `ours`, `theirs` | label, missing target |
| `duplicate-id` | both added different items under one id; two variables of one name (`merge.conflict.duplicateName{0}`) | the item; `variable/<id>/name` | `ours`, `theirs` | label; the name |
| `rebuild-failure` | fails only in the merge | `…/rebuild` | `accept` | label, error |
| `blob` | both replaced one opaque value | the value | `ours`, `theirs` | label, field |

Conflicts are ordered: document fields, variables, acts, materials, components, then nodes in merged
pre-order (inside a node: properties in rule order, then payload items in merged list order; a node
the merge deleted comes after its nearest preceding node in base pre-order), then `rebuild-failure`s in
the same node order. `merged` always holds the first choice; `resolveMerge(result, choices)` re-merges
with the user's choices (re-applied by path) and lists what is left. Choices accumulate:
`MergeResult.resolutions` are the choices applied so far and `resolved` the conflicts they answered; a
later `resolveMerge` keeps them (a new choice for the same path replaces the old one) and accepts a
path from `conflicts` or `resolved` — so a conflict a resolution created (a cycle, a new dangling
reference) is resolved without undoing the first. The conflict panel (CLOUD-13) reapplies its choices with `reapplyResolutions`
(`packages/cloud/src/conflicts/`): `resolveMerge` in rounds, so choices for conflicts other choices
create apply in one call, and the choices whose path a re-merge no longer has come back as `dropped`.

### Paths

A path is `/`-separated segments built with `mergePath(root, …segments)`, each segment escaped like a
JSON Pointer token (`~` → `~0`, `/` → `~1`). **Only ids, keys and fixed words — never array
indexes** — so after a re-merge onto a newer head (a remote update during resolution), the same
conflict has the same path and CLOUD-13 re-applies the user's choice by path.

```
doc/name · doc/settings/<key> · doc/userData/<key> · doc/<field> (any other top-level field)
variable/<variableId>[/<field>]                      field: name | type | expression | description
act/<name>[/#<n>][/<field>]                          #<n>: the n-th act of one name (n ≥ 2)
material/<id>[/<field>] · component/<id>[/<field>]
node/<id>                                            the node itself (delete-vs-modify, duplicate-id)
node/<id>/parent · node/<id>/position · node/<id>/rebuild
node/<id>/prop/<property>[/<key>…]                   a property (a blob, a primitive parameter, a payload that is not JSON)
node/<id>/content                                    the rest of a node of an unregistered class (one value)
node/<body>/feature/<featureId>[/param/<key>]        a feature, a parameter or a group (param/input, param/axis)
node/<body>/feature/<featureId>/position | /rebuild
node/<body>/insertAfter/<featureId> · node/<body>/insertAtStart
node/<sketch>/entity/<entityId>[/<field>]
node/<sketch>/constraint/<constraintId>[/<field>]
node/<sketch>/external/<entityId>[/<field>]
node/<sketch>/anchor/<constraintId> · node/<sketch>/refPosition/<bodyId>
node/<construction>/definition/<field>               a payload's own root (MergePayloadRule.segment):
node/<sketch>/planeRef · node/<sketch>/constructionPlaneRef
```

A `Change` and a `MergeConflict` about the same thing share their path; `isWithinMergePath` groups
them by node (`node/<id>` contains everything below it) for the panel's grouping and highlighting.

## Change model (diff and Compare)

`Change = { kind, path, nodeId?, before, after, messageKey, args }` (`types.ts`), kind `added` ·
`removed` · `modified` · `renamed` · `moved` · `reordered`. It is what `diffDocuments(base, next)`
returns (`Result<Change[], DocumentFormatError>`, both migrated first), and what a clean merge's "View
changes" lists (`MergeResult.changes` = `ours` → `merged`). The diff walks the same rules as the merge
(two-way), at the same granularity; recomputed values (`derived`) and the legacy counters (`max` /
`min`) are not reported:

- `added` / `removed` — a node, feature, sketch entity / constraint, variable, act, material
  (`diff.added{0}`, `diff.removed{0}`);
- `renamed` — a `name` change (`diff.renamed{0}{1}`), reported besides any other change of the same
  item (as the placeholder does);
- `modified` — one value, with before/after (`diff.changedValue{0}{1}{2}{3}`: label, field, before,
  after — "Extrude 3: depth 10 → 15 mm"; values formatted by the UI), or `diff.modified{0}` when the
  value is not displayable (a blob, a selection);
- `moved` — a new parent (`diff.moved{0}`); `reordered` — a new position in a timeline
  (`diff.reordered{0}`); sibling reorders in the tree are not reported.

`nodeId` is the node the change belongs to (for highlight and grouping); `undefined` for document
fields, variables, acts and materials.

**Compare** (the version history, CLOUD-09) lists `summarizeChanges(changes, before, after)` lines
through the registered `IDocumentDiffer` (`DocumentDiffers`, default `SemanticDiffer`): display names
("Extrude 3" — a feature's name, else its type and 1-based place; "Box 1" from `body.box1`), values in
the document's length unit or degrees ("Extrude 3: depth 10 mm → 15 mm"), what is inside an added or
removed node not listed again, and a sketch's items summarized in one line ("Sketch 2: +3 lines,
−1 constraint").

## Unique ids

Merging by id needs ids that two devices never hand out for different things. Audit of every id
allocator:

| Id | Allocation | Global? | Action |
|----|-----------|---------|--------|
| Node ids (all nodes, annotations, construction nodes, analyses) | `Id.generate()` (21-char nanoid) | yes | none |
| Feature ids | `Id.generate()` (commands, `parametricProgram.ts`) | yes | none |
| Variable, material, component, analysis-definition ids | `Id.generate()` | yes | none |
| Document ids; copies (`transferDocument`) get a new one | `Id.generate()` | yes | none |
| **Sketch entity ids** | were `entityIdSeq++` per sketch (`solver.ts`), `max + 1` for copies (`utilityOperations.ts`) | **no** | random |
| **Sketch constraint ids** | were `max + 1` (`nextSketchId`) | **no** | random |
| **Sketch external entity ids** | were `externalIdSeq--` from −100 (`externalEntities.ts`) | **no** | random (≤ −101) |
| External ids of a sketch created on a face | counted from −100 (`captureFaceBoundaryRefs`) | the sketch is new | kept |
| Entity / constraint ids of the MCP `sketch` op | counted from 1 (documented: "the 1-based position in entities") | the sketch is new | kept (`sequentialSketchIds`) |
| Tracked sub-shape ids (`f1:0`, `a\|b`, `tool:<node>:<n>`, seeds) | *derived*, not allocated: feature id + kernel history index / sketch-entity seeds | yes (from global ids) | none — must stay deterministic across rebuilds, and does |
| Node names (`Box1`, `Box2`…) | `max + 1` per base name (`NodeUtils.generateName`) | no | none — names are not identity; two devices may both make `Box3`, both are kept |
| Acts | no id | — | keyed by name (open question) |

The sketch fix (`sketchIds.ts`): every entity, constraint and external id added to an **existing**
sketch is drawn at random from 2^40 values (collision-checked against the sketch, redrawn on a hit).
Two devices each adding n items collide with probability ≈ n²/2^40 (5·10⁻⁹ for 50 each), and a
collision is still caught (`duplicate-id`), never fused. 2^40 keeps ids within 13 digits (agents read
them through MCP) and far inside `Number.MAX_SAFE_INTEGER`, exact in JSON and every `number` path.
Ids never go into typed arrays or the PlaneGCS tags (the solver maps them to its own indices), and
`ProfileRef.entities` sorts them numerically.

Counting is kept only where the sketch is created in the same session — no other version can hold
it, and the sketch's own nanoid keeps it apart: the MCP `sketch` op (its documented 1-based ids) and
the boundary externals of a sketch created on a face.

**No migration.** The stored type is unchanged — integers, positive for entities and constraints,
≤ −100 for externals — so existing documents keep their ids and load and rebuild identically
(`sketchIds.test.ts` round-trips every stored sketch; the parametric suites pass). The random draw
also keeps the old guarantee the counters were for: a freed id is (with overwhelming probability)
never reissued, so a stale `ProfileRef.entities` set cannot hit a new region. The former counters
`entityIdSeq` / `externalIdSeq` stay in the type as legacy fields: carried verbatim where a document
has them (a no-op edit session stays byte-identical), never written for new sketches, never read;
the merge takes their max / min.

## The rule registry

Rules are declarations the engine interprets (`MergeClassRule`, `MergePayloadRule`,
`MergeValueRule` in `rules.ts`). Each module registers the rules of the classes it registers with
the serializer, next to them (`registerMergeRule(className, rule)`, `registerMergePayload(name, rule)`).

- A new `@serializable` class needs a rule: `packages/builder/test/mergeRules.test.ts` fails
  otherwise — it checks every class the serializer registers at runtime, and every class a source
  file declares `@serializable` (a static scan, which also covers modules no entry point imports).
  The explicit fallback is `strategy: "atomic"` — allowed, but it has to be declared.
- Changing a payload's shape (a `registerMigration` step) means updating its payload rule.
- The list below is generated from the registry; the same test fails when it is stale and
  `npm run merge:rules` rewrites it.

## Open questions

- **Acts have no id.** They are keyed by name; two acts renamed differently on each side become two
  acts. An `id` on `Act` is a format bump (document module) with a migration and a v2 fixture — worth
  doing with the next core format change.
- **`FuseNode` is dead code**: declared `@serializable` but imported by no entry point, so documents
  with one would not load. It has a rule (the static scan found it); should it be registered or
  removed?
- **Timeline-insert conflicts at the end** (kept as written for CLOUD-12). Two devices appending features at the end of the same
  body conflict (their order changes the geometry). If that proves noisy, appends of features that
  touch disjoint sketches could be ordered deterministically instead.
- **Name LWW** takes `theirs` (the head) when both renamed the document; CLOUD-13 may prefer to show
  it as a conflict — it is a one-line rule change.
